# Cloud Engineer Test - Async Media Processing on AWS

Take-home assignment solution: a small asynchronous media-processing app
(public HTTP API + private background worker + PostgreSQL + S3) running as
containers on AWS Fargate and provisioned with Terraform.

- **API** - public HTTP API: upload video, apply an operation (convert, resize,
  compress, grayscale), poll status, download via presigned URL.
- **Worker** - private Fargate task that polls PostgreSQL for pending jobs and
  runs `ffmpeg` on files in S3.
- **Infrastructure** - 100% Terraform, applied per-environment (`dev`, `prod`).

---

## Architecture

```
                     Internet
                         |
                    ALB (public, HTTP:80)
                         |
              +----------+-----------+                 +------------------+
              |  API task (private)  |--- DB --->      |  RDS PostgreSQL  |
              |  Fargate, awsvpc      |                 |  (private subnet)|
              +----------+-----------+                 +------------------+
                         |                              |                  |
                    S3 media bucket                  [ jobs table = queue ]
                         ^                              ^                  |
              +----------+-----------+                  |                  |
              | Worker task (private)|------------------+   via SG rules   |
              | Fargate, ffmpeg       |
              +---------------------+
```

Traffic flow:

1. Client uploads a file to `POST /upload` on the ALB. The API stores the file
   in S3 and records a `session` in PostgreSQL.
2. Client submits `POST /sessions/{id}/apply`. The API inserts a `job` row with
   `status = pending` (the DB `jobs` table acts as the job queue).
3. The worker `ClaimNextJob` uses `FOR UPDATE SKIP LOCKED` to atomically claim
   one pending job, downloads the input from S3, runs `ffmpeg`, uploads the
   result back to S3, then advances the session version and marks the job done.
4. The client polls `GET /sessions/{id}/status` and finally
   `GET /sessions/{id}/download`, which returns a 15-minute presigned S3 URL.

### Main architecture choices

| Concern | Choice | Why |
| --- | --- | --- |
| Containers | **ECS Fargate** (`awsvpc`) | Serverless, no EC2 to manage; each task gets its own ENI and SG, so worker/API/DBSG rules stay tight. Simpler than EKS for this scope. |
| Public entry point | **ALB** on port 80 | Standard HTTP routing + health checks (`/healthz`), target-type `ip` for Fargate. |
| Queue | **PostgreSQL `jobs` table** + `SKIP LOCKED` | The assignment allows "a database or job queue"; using the existing DB avoids an extra service while staying correct under concurrency. |
| Database | **RDS PostgreSQL 16** (`db.t3.micro`) | Private subnet, storage encrypted, only ECS SG can reach 5432. |
| Object storage | **S3** (`media-{env}-files`) | Server-side encryption (AES256), versioning on, public access fully blocked; downloads only via presigned URLs. |
| Images | **ECR**, one repo per service | `scan_on_push = true`; `IMMUTABLE` tags in prod so tags always map to one digest. |
| Secrets | **AWS Secrets Manager** | DB password generated at apply (`random_password`), stored in a secret, injected at runtime (see below). |
| Logs | **CloudWatch Log Groups** via `awslogs` driver, Container Insights on | Centralized logs with 14-day retention. |
| Network | VPC, 2 AZs, public + private subnets, NAT gateway | Worker and DB have **no public access**; egress via NAT for pulling images / reaching AWS APIs. |
| IAM | Two task roles | Least privilege: execution role (pull image, write logs, read secret) separate from task role (S3 ops, read secret). |

### How containers receive secrets securely

- The DB password is generated by Terraform (`random_password`) and written
  **only** into two places: the RDS instance and an AWS Secrets Manager secret
  (`terraform/modules/secrets/main.tf`). It never appears in git, a `.env`, a
  container image, or plaintext task config.
- Task definitions reference secret values as Secrets Manager ARNs in the
  container `secrets` block, e.g.:
  `"${module.secrets.db_secret_arn}:DB_HOST::"`. ECS fetches them at task start.
- The **execution role** holds `secretsmanager:GetSecretValue` scoped to that
  secret's ARN only (`terraform/modules/iam/main.tf`).
- The app just reads env vars (`app/internal/config/config.go`); it never sees
  a hardcoded credential.

### How the worker communicates with the API / database

There is no worker→API call. The worker only talks to:

- **PostgreSQL** - `ClaimNextJob()` atomically claims a pending row
  (`FOR UPDATE SKIP LOCKED`), so multiple workers can poll without double
  processing. Job outcome is written back via `CompleteJob`/`FailJob`.
- **S3** - downloads the input object, uploads the processed output.

The API and worker are both in private subnets behind the same ECS SG; the RDS
SG only allows inbound 5432 from that ECS SG. No public routes exist for the
worker, database, or bucket.

### How container versions are deployed and rolled back

- Images are built with **versioned tags** (`1.0.0`, ...) and referenced via
  `api_image_tag` / `worker_image_tag` in `terraform.tfvars`. `latest` is the
  dev-only default; prod uses `IMMUTABLE` tags.
- **Deploy:** build/push the image to ECR with the new tag, bump the tag in the
  environment's `terraform.tfvars`, run `terraform plan`/`apply`. The ECS
  service starts a rolling deployment with zero downtime (Fargate replaces
  tasks one at a time).
- **Roll back:** set the tag back to the previous value and re-apply. Because
  tags map to a single digest (immutability in prod), the old image is
  guaranteed to still be pullable.

## Testing the live dev API

> **Dev only - not production-ready.** The base URL below points at the `dev`
> environment ALB. It is HTTP-only (no TLS), unauthenticated, has no rate
> limiting, and may be rebuilt/restarted at any time. Use it only to try the
> flow, not for anything real.

**Base URL:** `http://media-dev-alb-1228361591.eu-central-1.elb.amazonaws.com`

| Endpoint | Method | Description |
| --- | --- | --- |
| `/healthz` | GET | Liveness/health check |
| `/upload` | POST | Multipart upload, field `file` |
| `/sessions/{id}/apply` | POST | Queue an operation (JSON body) |
| `/sessions/{id}/status` | GET | Session + latest job status |
| `/sessions/{id}/download` | GET | Presigned S3 URL (15 min) |

Operations for `apply`: `convert` (needs `format`, e.g. `webm`), `resize`
(needs `width`, `height`), `compress` (optional `crf`), `grayscale`.

```bash
BASE=http://media-dev-alb-1228361591.eu-central-1.elb.amazonaws.com

# 1. health
curl -s "$BASE/healthz"

# 2. upload
curl -s -F "file=@app/demo/snail.mp4" "$BASE/upload"

# 3. apply an operation (use the session_id from step 2)
curl -s -X POST "$BASE/sessions/<SESSION_ID>/apply" \
  -H "Content-Type: application/json" -d '{"operation":"grayscale"}'

# 4. poll until job.status == "done"
curl -s "$BASE/sessions/<SESSION_ID>/status"

# 5. download result
curl -s "$BASE/sessions/<SESSION_ID>/download"
```

There is also a ready-made parallel smoke test in `app/demo/test-demo.bat`
(uploads both sample videos, applies the operation, polls, saves results to
`app/demo/output/`).

## Getting started (infra)

Requirements: Terraform >= 1.5, AWS CLI with credentials for the target
account, `terraform.tfstate` bucket already created (see `backend.tf`).

```bash
cd terraform/environments/dev
terraform init
terraform plan
terraform apply
```

Repeat in `prod/` with `-var-file=terraform.tfvars`. State is stored in a
shared encrypted S3 backend with a lock file
(`cloud-engineer-tfstate-790139457078`, key `environments/{env}/terraform.tfstate`).

## If the API works but the worker processes no jobs - three checks

1. **Are pending jobs stuck in the DB?** Query `SELECT status, count(*) FROM
   jobs GROUP BY status;` and check the latest `jobs.error`. A repeated
   `ClaimNextJob` error in CloudWatch usually points at DB connectivity.
2. **Worker CloudWatch logs / task state.** Open the worker log group
   (`/ecs/media-{env}-worker`) and the ECS service events. If the task is
   crash-looping, the service `desired_count` won't be met; if it's unhealthy,
   `ffmpeg` may be failing on the input download.
3. **Does the worker have the right IAM + network access?** Verify the task
   role can `s3:GetObject`/`PutObject` on the bucket and that the ECS SG is
   still allowed inbound to the RDS SG (5432) and egress to NAT. A
   `failed to download input` error combined with an S3 `AccessDenied`
   indicates a stale role/policy after an apply.

## Current limitations

This is a deliberately simple solution, not a production-complete platform:

- **Keys & credentials are managed, but not yet automated end-to-end.** The DB
  password is generated at `terraform apply` and stored in Secrets Manager; no
  AWS-managed KMS key is specified (defaults to AWS-managed), there is no
  secret **rotation** schedule, and the AWS account admin credentials are
  assumed to live outside the repo (nothing is committed - `.env*`, `*.tfvars`
  (except examples) and `*.tfstate` are gitignored).
- **No CI/CD.** `.github/workflows/` is empty, so deployments are manual
  `terraform apply` from a local machine; there are no GitHub secrets or an
  OIDC-based deploy role yet.
- **No HTTPS.** The ALB listens on HTTP:80 only (no ACM certificate / domain).
- **Simple queue.** The DB-as-queue is fine at this scale but lacks SQS
  features (visibility timeouts, DLQs, dead-letter handling for stuck
  `processing` jobs after a worker crash).
- **Queue/SQS evolution: intended but not yet implemented.** A future move to a
  dedicated SQS queue (with visibility timeouts and a DLQ) plus DynamoDB as the
  session/job metadata store would decouple the worker from PostgreSQL, avoid
  locking `jobs` rows, and give per-message retry semantics. It is deliberately
  out of scope for this iteration; only the design intent is noted here.
- **Single-AZ NAT, single ALB** - no high availability on the ingress/NAT
  path; ECS and RDS do span 2 AZs.
- **RDS hardening is light:** `deletion_protection = false`,
  `skip_final_snapshot = true`, `backup_retention_period = 1` day.
- **App simplicity:** no auth/rate-limiting on the API, no upload size
  validation beyond the multipart parser, no retry/backoff for the worker's
  S3/Db calls, and operations are limited to the four ffmpeg presets.
- **GPU inference service: intended but not yet implemented.** The architecture
  leaves room for a private GPU service (added as a third Fargate/ECS service in
  private subnets) that processes inference jobs handed off via the DB or a
  separate SQS queue and scales to zero when idle. It is deliberately out of
  scope for this iteration; only the design intent is noted here.
